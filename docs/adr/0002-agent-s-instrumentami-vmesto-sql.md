# 2. Агент с инструментами вместо SQL от модели

Дата: 2026-10-26

## Статус

Принято

## Контекст

Платформа отвечает на вопросы по данным. В первой версии это был
конвейер text-to-SQL: модель за один вызов возвращала JSON с намерением
и готовым SQL, платформа проверяла его в `sqlguard` и выполняла, а при
ошибке просила модель переписать запрос.

У такого конвейера две слабости.

1. **Безопасность держится на разборе чужого текста.** `sqlguard` ищет
   опасное в строке, которую написала модель: запрещённые слова, функции,
   системные схемы. Это чёрный список. Всё, что мы не перечислили,
   проходит. Модель при этом может написать что угодно, а подсказать ей
   «что угодно» может и текст внутри загруженных данных (prompt injection).
   Вдобавок API подключался к базе владельцем — в стенде суперпользователем
   образа `postgres`. Обход лексера означал бы доступ к `pg_read_file`
   и к таблице с ключами провайдеров моделей.
2. **Один выстрел вместо рассуждения.** Модель не видела данных до ответа:
   не могла посмотреть значения колонки, проверить промежуточный результат
   или собрать ответ из нескольких запросов. Сценарии 7–10 ТЗ (сезонность,
   лаги, прогноз) малая локальная модель в SQL почти наверняка испортит.

Эксперт хакатона отдельно отметил, что защите text-to-SQL будет уделено
особое внимание, и предложил дать модели готовый инструментарий, «чтобы
она ничего не могла сделать».

## Решение

### Модель не пишет SQL

Модель вызывает типизированные инструменты, описанные JSON Schema:
`describe_dataset`, `aggregate`, `sample_rows`, `find_duplicates`,
`seasonality`, `correlate`, `forecast`, `find_anomalies`, а также
`create_dashboard`, `add_to_dashboard`, `remove_widget` и финальные
`answer`, `clarify`, `decline`.

Главный из них — `aggregate`: модель заполняет поля «датасет, метрики,
разрезы, период, фильтры, сортировка», а SQL собирает пакет
`core/analytics`:

- датасеты и колонки — только из каталога, по точному совпадению;
- функции агрегации, операторы и шаги времени — только из перечислений;
- значения фильтров приводятся к типу колонки в Go и уходят в базу
  параметрами `$1`, а не текстом запроса;
- сортировка — по номеру колонки результата, выражение в неё не попадает;
- соединения — только по связям, которые платформа вывела сама;
- пределы на число метрик, разрезов, фильтров, соединений и строк.

Это белый список: вредный запрос в таком языке невыразим. Строку
`'; DROP TABLE` можно передать только как значение фильтра, и она
останется значением.

Свободный SQL оставлен инструментом `run_sql` за флагом
`AGENT_ALLOW_RAW_SQL`, выключенным по умолчанию. Без инструментов
(модель или сервер без function calling) план тоже описывает запрос
полем `query`, а SQL от модели отклоняется и уходит на починку.

### Три слоя защиты

| Слой | Что гарантирует | Где |
|---|---|---|
| Компилятор запросов | Модель выбирает только из разрешённого; значения — параметры | `core/analytics` |
| `sqlguard` | Даже собранный платформой SQL — только `SELECT` по таблицам каталога, с пределами | `core/sqlguard` |
| Роль `aibi_reader` | `SELECT` только на схему данных, read-only по умолчанию, без доступа к `public` и функциям суперпользователя | `corepg.EnsureReaderRole` |

Слои не доверяют друг другу. Интеграционный тест
`TestReaderRoleIsolation` выполняет под ролью чтения запросы, которые
специально обходят первые два слоя, и проверяет, что база их отклоняет.

Пароль роли чтения генерируется заново при каждом старте и нигде не
хранится. Транзакция аналитического запроса — `READ ONLY` с
`statement_timeout`. Результаты инструментов промпт явно помечает как
данные, а не инструкции, но защита на этом не держится: даже
«уговорённая» модель может только вызвать инструмент чтения.

### Агентный цикл

Модель ведёт разговор с инструментами по протоколу function calling
OpenAI. Его понимают Ollama, vLLM, llama.cpp и OpenRouter. Модель
вызывает инструмент, видит результат или текст ошибки, исправляет
параметры и продолжает, пока не вызовет `answer`, `clarify` или
`decline`. Предел — `AGENT_MAX_STEPS`. Самопочинка, которая раньше была
отдельным шагом конвейера, стала естественной частью цикла: ошибка
компилятора возвращается модели как результат инструмента.

Ход работы (`Answer.Steps`) сохраняется в ответе и показывается
пользователю. Видно, какие инструменты вызывались и где модель
ошиблась и исправилась.

### Статистика в Go, а не в модели

Сезонность, корреляция с лагом, прогноз и выбросы считаются в
`core/analytics/stats.go` по ряду, который агрегирует тот же компилятор.
Модель выбирает, что анализировать, и пересказывает результат.
Арифметика воспроизводима и покрыта табличными тестами.

### MCP

Инструменты чтения доступны и внешним агентам по Model Context Protocol
(`POST /api/v1/mcp`) с теми же проверками. Дашборды, `run_sql` и
финальные ответы наружу не отдаются.

## Последствия

- Вопрос, не укладывающийся в инструменты, агент не решит без `run_sql`.
  Это осознанная цена: выразительность обменяна на гарантию. Набор
  инструментов расширяется кодом, а не промптом.
- Ответ занимает несколько обращений к модели вместо одного-трёх. На
  слабом железе это заметно, поэтому предел шагов настраивается.
- Виджет дашборда хранит параметры запроса (`dashboard_widgets.query`),
  а не SQL. При каждом открытии он пересобирается и заново проходит все
  проверки. На этом же строятся будущие общие фильтры панели: фильтр
  добавляется к параметрам, а не вклеивается в SQL.
- Для роли чтения владельцу базы нужно право `CREATEROLE`. Где его нет,
  `PG_READER_ROLE` оставляют пустым, и запросы идут от владельца — это
  явно пишется в лог при старте.
- Модели без function calling продолжают работать через план в JSON, а
  без модели платформа описывает данные по профилю каталога.
