# Длительности и сравнение периодов

Агент считает интервалы и проверяет изменение показателя через типизированные
параметры. Свободный SQL не требуется; каждый запрос проходит `sqlguard` и роль
чтения, как обычный `aggregate`. Те же инструменты доступны через MCP.

## Длительность как метрика

Вместо `column` или числовой формулы `expr` указывается `duration`:

```json
{
  "fn": "median",
  "duration": {
    "start": "Создано (МСК)",
    "end": "Начало работы (МСК)",
    "unit": "hour"
  },
  "label": "Медиана ожидания, ч"
}
```

Поддерживаются `minute`, `hour`, `day` и функции `avg`, `median`, `p90`, `min`,
`max`, `sum`, `share`, `count`. Длительности доступны в `aggregate`,
`compare_segments` и метриках временных инструментов. `p90` также работает с
числовой колонкой и формулой. `duration` нельзя смешивать с `column`, `expr`,
`per` или изменением колонки через `scale`.

Календарные часы не равны рабочим часам и трудозатратам. Пропущенные даты и
интервалы с концом раньше начала дают `NULL`, не ноль. `count` с `duration`
показывает число корректных интервалов; обычный `count` — все строки. Для
оценки полноты агент должен запросить оба счётчика.

Для Q1 «При каких условиях крупные задачи дольше ждут начала работы?» агент:

1. Выбирает набор и уточняет определение крупной задачи, если его нет в контексте.
2. Фильтрует по согласованным плановым трудозатратам, а не фактическим.
3. Считает ожидание от создания до начала работы по приоритету, типу и команде:
   медиану, P90, общее количество и число измеренных интервалов.
4. Сопоставляет размеры групп; отличает наблюдаемую связь от причины задержек.

`compare_segments` по умолчанию выбирает крупнейшие группы. Для поиска самых
долгих ожиданий нужен `aggregate` с сортировкой по медиане ожидания, а не числу строк.

## Инструмент compare_periods

Пример после согласования показателя, периодов и даты среза:

```json
{
  "dataset": "Задачи команд",
  "time_column": "Начало работы (МСК)",
  "metric": {
    "duration": {
      "start": "Начало работы (МСК)",
      "end": "Завершено (МСК)",
      "unit": "hour"
    }
  },
  "baseline": {"from": "2026-09-01", "to": "2026-09-11"},
  "current": {"from": "2026-09-21", "to": "2026-10-01"},
  "group_by": ["Команда", "Тип задачи", "Плановые трудозатраты, ч"],
  "direction": "lower",
  "observed_until": "2026-10-08",
  "followup_hours": 168
}
```

Даты и горизонт в примере не являются автоматическими определениями «конца
сентября» и даты среза. Из максимальной даты завершения нельзя вывести, что
все задачи наблюдались до этого момента.

- `baseline`, `current`: непустые непересекающиеся периоды; новый следует за
  базовым. `from` включается, `to` исключается. Даты и время интерпретируются
  в часовом поясе исходных данных, без неявного перевода МСК в UTC.
- `time_column`: дата формирования когорты. Для длительности выполнения
  обычно начало работы. Выбор завершения образует другую, смещённую выборку;
  инструмент предупреждает об этом.
- `metric`: ровно одно из `column`, `expr`, `duration`. Сравниваются
  распределения индивидуальных значений, не суммы и не средние по дням.
- `group_by`: до трёх признаков. Каждая комбинация сравнивается только с той
  же комбинацией другого периода. Не встретившиеся во втором периоде группы
  не исчезают и не получают нулевую среднюю.
- `direction`: `lower` — уменьшение желательно; `higher` — увеличение.
- `filters`: те же типизированные условия, что у `aggregate`. Отбор только
  завершённых задач скрывает незавершённые и не подходит для Q2.
- `observed_until`: фактическая исключительная граница наблюдения, только
  для `duration`. Конец изучаемого периода не может быть позже этой границы.
- `followup_hours`: одинаковый горизонт от начала интервала, до 8784 часов;
  требует `observed_until`. Интервал без полного горизонта считается
  недонаблюдённым. Завершение позже горизонта не включается в среднее и
  учитывается в незавершённых в окне.

Результат для каждой группы содержит объёмы когорт и измерений, среднее,
медиану, P90, разницу средних `current − baseline`, процентное изменение,
пропуски, некорректные интервалы, незавершённые в окне и недонаблюдённые задачи.
Последние счётчики могут пересекаться: складывать их нельзя. При нулевом
базовом среднем процент не определён и возвращается `null`.

Двусторонний интервал Уэлча относится к **разнице средних**, не медиан или P90.
Семейный уровень доверия — 95%, с поправкой Бонферрони по группам текущего
вызова. Нужно не менее 30 измерений в каждом периоде и ненулевой оцениваемый
разброс. При меньшей выборке интервал и p-значение не выдаются.

## Ограничения выводов

- При неполных интервалах или отсутствии общего горизонта наблюдения
  вывод помечается как **только описательное сравнение**. Интервал для
  завершившейся части когорты не превращает её в репрезентативную выборку.
- Усечённые результаты и слишком большое число групп отклоняются: нельзя
  сравнивать две случайно обрезанные половины выборки.
- Расчёт не исправляет цензурирование методом анализа выживаемости.
- Независимость наблюдений — допущение. Кластеризация по исполнителям,
  временная зависимость и другие неуказанные факторы не корректируются.
- Группировка контролирует только указанные признаки. По общему среднему
  нельзя заключить, что ускорилась каждая команда.
- Поправка действует в одном вызове, а не на всю историю исследовательского
  поиска. Незначимое различие не доказывает равенство; значимое — причинность
  или практическую важность.

## Режим без tool calling

JSON-планировщик передаёт `{"intent":"query","comparison":{...}}` с теми же
параметрами. `comparison` нельзя смешивать с `query` или `sql`. Без доступной
модели сохраняется обычное описание по каталогу, без выдуманного результата.

Параметры сравнения сохраняются в `Answer.Query` и полностью передаются в
историю, чтобы можно было продолжить анализ с другой группировкой или периодом.
Производное сравнение не закрепляется на дашборд как обычный SQL-виджет: для
такого виджета нужна отдельная поддержка пересчёта статистики. Длительности
в обычном `aggregate` пересчитываются на дашборде штатно.

Проверки:

```bash
go test -race ./...
TEST_DATABASE_URL=postgres://.../aibi_test go test -race -tags=integration ./internal/integration/... -run TestTaskDurationsAndPeriodComparisonOnPostgres
```

Интеграционным тестам нужна отдельная тестовая база: их подготовка удаляет
тестовые таблицы и схему. Не используйте рабочую базу платформы.
